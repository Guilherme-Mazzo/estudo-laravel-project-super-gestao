    Parte 1 Base

    Como a web funciona

    Antes de qualquer código: o que acontece quando alguém digita um endereço no navegador. Se esta parte ficar clara, rotas, controllers e views passam a fazer sentido quase sozinhos.

    1.1Cliente, servidor e o restaurante

    Toda vez que você abre um site, duas partes conversam. O cliente é o seu navegador (Chrome, Edge, o app do celular). O servidor é um computador que guarda e executa o sistema. O cliente faz um pedido, o servidor devolve uma resposta. Isso se repete a cada clique, a cada página aberta, a cada formulário enviado.

    Analogia

    Pense num restaurante. Você (cliente) olha o cardápio e faz um pedido ao garçom. O garçom leva o pedido para a pessoa certa na cozinha. O cozinheiro pega ingredientes no estoque, prepara e monta o prato. O garçom traz o prato até a mesa. Você nunca entra na cozinha: só vê o prato pronto.

    1.2Requisição e resposta (HTTP)

    HTTP é o idioma combinado entre cliente e servidor. Toda conversa tem duas metades:

    • Requisição (request): o pedido. Leva um método (GET, POST…), um endereço (/contato), cabeçalhos (informações extras, como o idioma do navegador) e às vezes um corpo (os dados de um formulário).
    • Resposta (response): o que volta. Leva um código de status (200, 404…), cabeçalhos e o corpo (normalmente o HTML da página).
    Na prática

    Veja isso de verdade: abra seu projeto no navegador, aperte F12, vá na aba Rede (Network) e recarregue a página. Clique na primeira linha: você verá o método, o status e todos os cabeçalhos. Essa aba é sua melhor amiga para depurar backend.

    Atenção

    O HTTP não tem memória. Cada requisição é independente, como se o garçom esquecesse você depois de cada prato. É por isso que existem sessões e cookies (o "cartão de cliente" que o navegador mostra a cada pedido). Isso aparece quando o curso chegar no login.

    1.3Métodos HTTP (os verbos)

    O método diz a intenção do pedido. O mesmo endereço pode fazer coisas diferentes dependendo do verbo.

    VerboIntençãoNo restauranteNo Laravel
    GETBuscar / ver algo"Me mostra o cardápio"Route::get(), abrir uma página
    POSTEnviar / criar algo"Quero fazer um pedido"Route::post(), enviar formulário
    PUTSubstituir algo inteiro"Troque meu prato inteiro"Route::put(), editar cadastro
    PATCHAlterar só uma parte"Só tire a cebola"Route::patch()
    DELETEApagar"Cancela o pedido"Route::delete()
    No seu projeto

    Todas as suas rotas são GET. No route:list elas aparecem como GET|HEAD. O HEAD é um GET que só quer os cabeçalhos, sem o corpo; o Laravel cria junto automaticamente, você não precisa fazer nada.

    Atenção

    Formulários HTML só sabem enviar GET ou POST. Para PUT, PATCH e DELETE o Laravel usa um truque com a diretiva @method('PUT') (veja 8.14).

    1.4Anatomia de uma URL

    Cada pedaço do endereço tem um papel. As rotas do Laravel trabalham no caminho.

    http://localhost:80/contato/guilherme/2?origem=menu#formulario
    • Protocolo http://: o idioma da conversa (https é a versão criptografada).
    • Host localhost: qual servidor. "localhost" significa "esta própria máquina".
    • Porta :80: qual "ramal" do servidor. A 80 é o padrão do http e por isso costuma ficar oculta. No seu projeto ela vem de APP_PORT no compose.yaml.
    • Caminho (URI) /contato/...: é aqui que as rotas do web.php fazem a combinação.
    • Parâmetros de rota guilherme/2: pedaços variáveis, capturados por {nome} e {categoria_id}.
    • Query string ?origem=menu: dados extras opcionais no formato chave=valor, lidos com $request->query('origem').
    • Âncora #formulario: rola a página até um ponto. Nem chega ao servidor.

    URL é o endereço completo. URI é o "pedaço do caminho" (/contato/guilherme/2). No dia a dia muita gente usa como sinônimos; no Laravel o primeiro argumento de Route::get() é a URI.

    1.5Códigos de status

    O número que volta na resposta resume o que aconteceu. Basta lembrar das famílias: 2xx deu certo, 3xx vá para outro lugar, 4xx o cliente pediu errado, 5xx o servidor (a cozinha) errou.

    CódigoSignificadoQuando você vai ver
    200OKPágina carregou normalmente.
    201CreatedAlgo foi criado (comum em APIs).
    301Mudou de endereço para sempreRoute::permanentRedirect().
    302Redirecionamento temporárioPadrão de redirect() e Route::redirect(). Sua /rota2 responde 302.
    404Não encontradoNenhuma rota combinou com o endereço.
    405Método não permitidoA rota existe, mas com outro verbo (ex.: deu POST numa rota GET).
    419Página expiradaExclusivo do Laravel: formulário enviado sem @csrf ou sessão vencida.
    500Erro internoSeu código PHP quebrou. Todos os erros da Parte 9 foram 500.
    503IndisponívelModo manutenção (sail artisan down).

    1.6Frontend, backend e onde o PHP entra

    Frontend é o que roda no navegador: HTML (estrutura), CSS (aparência) e JavaScript (interação). Backend é o que roda no servidor: recebe o pedido, aplica regras, conversa com o banco e monta a resposta. O PHP e o Laravel vivem no backend.

    O navegador nunca recebe PHP. Ele recebe só o HTML que o PHP produziu. Faça o teste: abra sua página principal e aperte Ctrl+U (exibir código-fonte). Você verá <a href="http://localhost/sobre-nos"> e não {{route('site.sobrenos')}}. O Blade foi traduzido no servidor antes de sair.

    Analogia

    A receita fica guardada na cozinha. O cliente só vê o prato. Por isso dá para guardar senhas e regras de negócio no backend: elas nunca saem do servidor.

    Resumo da Parte 1
    • Cliente pede, servidor responde. Isso é uma requisição HTTP.
    • O método (GET, POST…) diz a intenção; o caminho diz o quê.
    • O status diz como terminou: 2xx ok, 3xx redireciona, 4xx erro do cliente, 5xx erro do servidor.
    • PHP roda no servidor e entrega HTML pronto.

    Parte 2 Base

    Laravel e o padrão MVC

    O que é um framework, como o Laravel organiza o código e o caminho completo que um pedido percorre dentro do seu projeto, arquivo por arquivo.

    2.1O que é um framework

    Um framework é um conjunto de código pronto e de regras de organização. Ele resolve os problemas que todo sistema web tem (rotas, páginas, banco de dados, segurança, login, e-mails) para você focar no que é específico do seu sistema.

    Analogia

    Montar um restaurante do zero significa comprar fogão, instalar gás, criar regras de higiene e organizar o estoque. Um framework é uma cozinha profissional já montada, com tudo no lugar e etiquetado. Você chega e cozinha. A contrapartida: você precisa aprender onde cada coisa fica e seguir as regras da casa.

    O Laravel segue a ideia de convenção em vez de configuração: se você puser cada coisa no lugar esperado e com o nome esperado, ele encontra sozinho. Controllers em app/Http/Controllers, views em resources/views, rotas em routes/web.php. Boa parte dos erros de iniciante é só uma coisa fora do lugar ou com o nome diferente do esperado.

    2.2MVC: Model, View, Controller

    MVC é uma forma de dividir o sistema em três responsabilidades, para que cada parte faça uma coisa só.

    CamadaResponsabilidadeNo restauranteVocê já usou?
    ModelDados e regras: ler e gravar no bancoO estoque e quem cuida deleAinda não. Existe um de exemplo: app/Models/User.php
    ViewO que o usuário vê (HTML)O prato montadoSim: resources/views/site/*.blade.php
    ControllerRecebe o pedido, coordena, devolve a respostaO chefSim: Principal, SobreNos e Contato

    A rota não é uma das três letras, mas é a porta de entrada: ela decide qual controller atende cada endereço.

    Regra de ouro

    A view não busca dados no banco. O controller não monta HTML com echo. O model não sabe que existe uma página. Quando cada camada faz só o seu trabalho, o código fica fácil de mudar, e é isso que as empresas esperam ver no seu código.

    2.5Composer e o autoload

    O Composer é o gerenciador de pacotes do PHP. Ele baixa o Laravel e as bibliotecas que o projeto usa e cria o autoload: o mecanismo que encontra o arquivo de uma classe só pelo nome dela.

    Analogia

    composer.json é a lista de compras ("quero Laravel 10"). composer.lock é a nota fiscal, com a versão exata de cada item comprado. vendor/ é a despensa onde tudo foi guardado. Quem clona o projeto roda composer install e recebe exatamente os mesmos itens da nota.

    A regra que liga nomes de classe a pastas se chama PSR-4 e está no seu composer.json:

    Tradução: tudo que começa com App\ mora na pasta app/. Então a classe App\Http\Controllers\ContatoController fica, obrigatoriamente, em app/Http/Controllers/ContatoController.php. O namespace é o "endereço" e precisa bater com a pasta.

    Atenção

    Seu código roda num container Linux, e no Linux maiúsculas importam no nome de arquivo. ContatoController.php e contatoController.php são arquivos diferentes. Se o nome do arquivo não for idêntico ao nome da classe, o autoload não encontra e você recebe "Class not found" ou "Target class does not exist".

    2.6Artisan, o assistente

    artisan é um programa de linha de comando que vem com o Laravel. Ele cria arquivos já no formato certo (make:controller), mostra informações (route:list) e faz manutenção (view:clear). No seu ambiente você o chama pelo Sail: sail artisan ....

    Analogia

    É o ajudante de cozinha experiente. Você pede "prepara um controller de fornecedores" e ele entrega o arquivo no lugar certo, com namespace, nome e herança corretos. Use sempre que puder: evita os erros de digitação da Parte 9.

    A lista completa de comandos está na Parte 4.

    2.7O arquivo .env

    O .env guarda configurações que mudam de máquina para máquina: nome do banco, senhas, se mostra erros detalhados. Cada linha é CHAVE=valor. Os trechos mais importantes do seu:

    • Nos arquivos de config/ os valores são lidos com env('APP_NAME'). No resto do código, use config('app.name').
    • O .env está no .gitignore e nunca deve ir para o GitHub. O .env.example é o modelo sem senhas que vai.
    • Mudou o .env e nada aconteceu? Rode sail artisan config:clear. Se mudou porta, reinicie: sail down e sail up -d.
    Atenção

    APP_DEBUG=true em produção expõe trechos do código e configurações para qualquer visitante. No trabalho, servidor de produção sempre com APP_DEBUG=false.

    Parte 3 Base

    Ambiente: Docker, WSL e Sail

    Por que o seu Laravel roda dentro de "containers", o que cada linha do seu compose.yaml faz e como o Windows, o WSL e o Docker conversam entre si.

    3.1O problema que o Docker resolve

    Um projeto Laravel precisa de PHP numa versão específica, extensões do PHP, um banco MySQL, às vezes Redis, servidor de e-mail de teste… Instalar tudo isso direto no Windows de cada pessoa da equipe gera o famoso "na minha máquina funciona".

    O Docker empacota cada serviço numa caixa isolada, com tudo que ele precisa, igual para todo mundo. Você não instala PHP nem MySQL no Windows: eles rodam dentro dessas caixas.

    Analogia

    Em vez de cada cozinheiro montar a própria cozinha em casa, a empresa entrega um food truck padronizado, idêntico para todos. Qualquer um liga o truck e tudo funciona do mesmo jeito.

    Os comentários foram adicionados para explicar e algumas linhas secundárias foram omitidas; o seu arquivo original não tem esses comentários.

    A sintaxe ${APP_PORT:-80} significa: "use o valor de APP_PORT do .env; se não existir, use 80". É o mesmo conceito de valor padrão que você usou nos parâmetros opcionais das rotas.

    No seu projeto

    Seu .env tem FORWARD_DB_PORT=3307, e o docker compose ps confirma: mysql 0.0.0.0:3307->3306. Ou seja, do Windows o banco está na porta 3307, mas dentro da rede Docker ele continua na 3306. Normalmente se faz isso quando já existe outro MySQL ocupando a 3306 na máquina.

    3.4WSL: um Linux dentro do Windows

    O WSL (Windows Subsystem for Linux) roda um Ubuntu de verdade dentro do Windows. O Docker Desktop usa o WSL por baixo, e o seu projeto mora no sistema de arquivos do Linux:

    • No Ubuntu: /home/guilherme/projetos/estudos-laravel (atalho: ~/projetos/estudos-laravel)
    • Visto pelo Windows: \\wsl.localhost\Ubuntu\home\guilherme\projetos\estudos-laravel
    Por que não deixar no C:

    Projetos guardados em /mnt/c/... (o disco do Windows visto pelo Linux) ficam muito mais lentos dentro do Docker e dão problemas de permissão. Manter no /home do Ubuntu, como você fez, é o recomendado.

    5.1Como um arquivo PHP é montado

    O PHP é uma linguagem interpretada no servidor: o código é lido e executado a cada requisição, linha a linha, e o resultado (geralmente HTML) é enviado ao navegador.

    • <?php abre o PHP. Precisa ser a primeira coisa do arquivo: até um espaço ou linha em branco antes dele vira "saída" e pode causar erro (veja 9.1).
    • ?> fecha o PHP. Em arquivos só de PHP, a convenção (PSR-12) é não fechar, para evitar espaços acidentais no fim.
    • ; termina instruções. Esquecer um ; gera erro que aponta para a linha seguinte.
    • Variáveis diferenciam maiúsculas: $nome e $Nome são diferentes. Nomes de funções, métodos e classes não diferenciam (mas os nomes de arquivo, no Linux, sim).

    6.2Anatomia de uma rota

    Vamos desmontar uma linha real do seu web.php:

    Route1::2get3('/contato'4, [ContatoController::class, 'contato']5)->name('site.contato')6;
    1. Route: uma Facade, a classe Illuminate\Support\Facades\Route importada no topo do arquivo. Ela é um balcão de atendimento: você fala com ela e ela repassa para o roteador de verdade (Illuminate\Routing\Router).
    2. ::: operador de chamada estática, "chame get na classe Route".
    3. get: o verbo HTTP que esta rota atende.
    4. '/contato': a URI, o caminho que precisa combinar.
    5. [Classe, 'método']: a ação. "Crie um ContatoController e chame o método contato." Também pode ser uma função anônima.
    6. ->name(...): um método encadeado. Route::get() devolve um objeto Route, e cada método dele devolve o próprio objeto, por isso dá para emendar ->name()->where()->middleware(). Isso se chama interface fluente.
    Analogia da Facade

    Você liga para o 0800 de um banco (a Facade) e fala "quero meu saldo". Quem atende repassa para o sistema certo lá dentro (o objeto Router). Você não precisa saber onde fica o sistema, só o número do 0800.

    6.5Parâmetros de rota

    Chaves na URI criam pedaços variáveis. O Laravel captura o valor e entrega para a função.

    A regra mais importante: posição, não nome

    O Laravel entrega os valores na ordem em que aparecem na URL. O nome dos parâmetros da função não importa: {nome} pode chegar em $x. Se você inverter a ordem na função, os valores chegam trocados, sem erro nenhum.

    Todo parâmetro chega como texto. Se você tipar como int, o PHP converte "2" em 2. Mas se chegar "abc", não há como converter e o resultado é um erro 500 (o seu erro 9.6). A solução é restringir com where() (6.7).

    6.6Parâmetros opcionais

    Um ? depois do nome torna o parâmetro opcional. Mas aí a função precisa de um valor padrão, para quando ele não vier.

    URL acessadaResultado

    /contato/ana/elogioNão combina (falta o assunto, que é obrigatório): cai no fallback

    Imagine /contato/{nome?}/{categoria} e alguém acessa /contato/financeiro. "financeiro" é o nome ou a categoria? Não dá para saber. Como o Laravel preenche da esquerda para a direita, os opcionais precisam ficar à direita, depois de todos os obrigatórios.     Route::fallback() é executada quando nenhuma outra rota combinou. Inclusive quando um where() recusa o valor.

    Dois ajustes importantes
    • Ela não redireciona. Seu comentário diz que o usuário "será redirecionado para a rota principal", mas o código mostra uma mensagem com um link. Para redirecionar de fato: return redirect()->route('site.index');
    • Ela responde 200 (OK). Para o navegador e para o Google, a página "existe". O correto é responder 404.
    Na prática: página 404 personalizada

    Crie o arquivo resources/views/errors/404.blade.php. O Laravel passa a usá-lo automaticamente sempre que algo der 404 (inclusive com abort(404)). Com ele, o fallback pode ser só Route::fallback(fn () => abort(404));.

    Sobre a posição: por organização, deixe o fallback sempre no fim do arquivo. O Laravel já o trata como última opção mesmo que esteja no meio, mas quem lê o código espera encontrá-lo no final.

    Fallback: "ele será redirecionado para a rota principal do site"Não há redirecionamento: a rota mostra uma mensagem com um link. Para redirecionar de fato: return redirect()->route('site.index').
    Na prática

    No trabalho, comentários explicam o porquê de algo não óbvio ("aceita só números porque o ID vem do sistema X"), não o que a linha faz. Para estudo, seus comentários longos estão ótimos; só não leve esse estilo para o código da empresa.

    Parte 13 Consulta

    Glossário

    Os termos que aparecem no curso e no trabalho, em linguagem simples. A busca no topo filtra os termos.

    13.1Termos de A a Z

    A

    Ação (action)
    O que uma rota executa: uma closure ou um método de controller.
    Alias
    Apelido para um comando. sail é um alias para vendor/bin/sail.
    API
    Um backend que conversa com outros programas (apps, frontends) trocando dados em JSON, em vez de devolver páginas.
    Array
    Coleção de valores numa variável. Associativo quando as posições têm nomes ('nome' => 'Ana').
    Artisan
    A ferramenta de linha de comando do Laravel (sail artisan ...).
    Asset
    Arquivo estático usado pela página: CSS, JavaScript, imagem, fonte. Fica em public/.
    Autoload
    Mecanismo do Composer que encontra o arquivo de uma classe pelo namespace dela.

    B

    Backend
    A parte do sistema que roda no servidor: regras, banco de dados, segurança.
    Bind mount
    Pasta do seu computador espelhada dentro de um container. É como o seu código aparece no Docker.
    Blade
    O sistema de templates do Laravel: arquivos .blade.php com {{ }} e @diretivas.

    C

    Callback
    Função entregue para outra função chamar depois. A closure de uma rota é um callback.
    Classe
    Molde que define dados (propriedades) e comportamentos (métodos) de um tipo de objeto.
    Closure
    Função anônima (sem nome), que pode capturar variáveis de fora com use.
    Compact
    Função do PHP que monta um array associativo a partir de nomes de variáveis: compact('p1') = ['p1' => $p1].
    Componente
    Peça de view reutilizável e configurável, usada como <x-alerta>.
    Composer
    Gerenciador de pacotes do PHP. Lê o composer.json e instala tudo em vendor/.
    Container
    Uma imagem Docker em execução: um ambiente isolado rodando um serviço (PHP, MySQL).
    Controller
    Classe que recebe o pedido vindo da rota, coordena o trabalho e devolve a resposta.
    CRUD
    Create, Read, Update, Delete: as quatro operações básicas de um cadastro.
    CSRF
    Ataque em que outro site envia formulários em nome do usuário. O @csrf protege contra ele.

    D

    Dependência
    Pacote ou classe de que o código precisa para funcionar.
    Diretiva
    Comando do Blade que começa com @: @if, @foreach, @extends.
    Docker
    Ferramenta que roda programas dentro de containers isolados e padronizados.
    Docker Compose
    Sobe vários containers juntos a partir de um arquivo (compose.yaml).

    E

    Eloquent
    O ORM do Laravel: trabalhar com tabelas do banco como se fossem classes PHP. Vem mais adiante.
    .env
    Arquivo de configurações e senhas da máquina. Nunca vai para o Git.
    Escapar
    Transformar caracteres especiais em texto inofensivo. {{ }} escapa HTML automaticamente.

    F

    Facade
    Atalho estático para um serviço do Laravel. Route::get() repassa a chamada para o roteador real.
    Fallback
    Rota de contingência, usada quando nenhuma outra combina.
    Framework
    Conjunto de código pronto e regras de organização para construir sistemas mais rápido.
    Frontend
    A parte que roda no navegador: HTML, CSS e JavaScript.

    H

    Helper
    Função global pronta do Laravel: route(), view(), asset(), redirect(), dd().
    Herança
    Quando uma classe recebe tudo de outra com extends. Seus controllers herdam de Controller.
    HTTP
    O protocolo (idioma) da conversa entre navegador e servidor.

    I

    Imagem (Docker)
    Molde pronto e só leitura a partir do qual containers são criados.
    Injeção de dependência
    O Laravel entrega automaticamente objetos que o método pede pelo tipo, como Request $request.
    Interpolação
    Colocar variáveis dentro de um texto com aspas duplas: "Olá, {$nome}".

    J · L

    JSON
    Formato de texto para trocar dados: {"nome":"Ana"}. Arrays devolvidos por controllers viram JSON.
    Layout
    View-modelo com a estrutura comum das páginas, usada com @extends.
    Log
    Registro de eventos e erros. No Laravel: storage/logs/laravel.log.

    M

    Método
    Função que pertence a uma classe. As ações dos controllers são métodos.
    Método HTTP (verbo)
    A intenção do pedido: GET, POST, PUT, PATCH, DELETE.
    Middleware
    Filtro que roda antes ou depois do controller (ex.: "só passa quem estiver logado").
    Migration
    Arquivo PHP que descreve a criação ou alteração de uma tabela do banco. Vem mais adiante.
    Model
    Classe que representa uma tabela do banco e suas regras.
    MVC
    Model, View, Controller: divisão do sistema em dados, visual e coordenação.

    N · O

    Namespace
    O "endereço completo" de uma classe, que também indica a pasta dela.
    Objeto
    Algo concreto criado a partir de uma classe com new.

    P

    Parâmetro de rota
    Pedaço variável da URL, escrito com chaves: {id}. Opcional com {id?}.
    Partial
    Pedaço de view incluído em outras com @include (ex.: o menu).
    Porta
    Número que identifica um serviço numa máquina: 80 (web), 3306 (MySQL), 5173 (Vite).
    PSR-4
    A regra que liga namespace a pasta: App\ → app/.

    Q · R

    Query string
    Dados extras na URL depois do ?: ?pagina=2&ordem=nome.
    Redirect
    Resposta que manda o navegador ir para outro endereço (status 301 ou 302).
    Regex
    Expressão regular: um molde que descreve o formato de um texto ([0-9]+).
    Request
    O pedido HTTP, e também o objeto do Laravel com todos os dados dele.
    Response
    A resposta HTTP: status, cabeçalhos e corpo.
    Rota
    Ligação entre um endereço (verbo + URI) e uma ação.
    Rota nomeada
    Rota com apelido (->name('site.contato')), usada para gerar links com route().

    S

    Sail
    Script que simplifica o uso do Docker em projetos Laravel.
    Sessão
    Memória do servidor sobre um visitante entre um pedido e outro (ex.: estar logado).
    Slot
    O conteúdo colocado entre as tags de um componente, impresso com {{ $slot }}.
    Stack trace
    A lista de chamadas que levou a um erro. Procure nela os arquivos do seu código.
    Status code
    Número que resume a resposta: 200, 302, 404, 419, 500…
    String
    Texto, entre aspas simples ou duplas.

    T · U

    Template
    Arquivo com estrutura fixa e espaços para dados. As views Blade são templates.
    Tinker
    Console interativo para testar código PHP com o Laravel carregado.
    Trait
    Pacote de métodos que pode ser "colado" em várias classes com use.
    URI / URL
    URL é o endereço completo; URI é o caminho (/contato), o que as rotas comparam.

    V · W · X

    Variável
    Caixa com nome que guarda um valor. No PHP começa com $.
    Vendor
    Pasta onde o Composer guarda o Laravel e os pacotes. Não se edita e não vai para o Git.
    View
    Arquivo que gera o HTML que o usuário vê.
    Vite
    Ferramenta que compila CSS e JS do projeto (sail npm run dev).
    Volume
    Espaço de dados do Docker que sobrevive quando o container é removido.
    WSL
    Windows Subsystem for Linux: um Linux rodando dentro do Windows.
    XSS
    Ataque que injeta código JavaScript numa página. Evitado com {{ }}.
